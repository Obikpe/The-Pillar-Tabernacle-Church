# Database Design

**Status:** Logical model proposal; SQL schema and migrations are not yet created.

## 1. Design principles

- PostgreSQL relational design.
- Stable primary keys (UUIDs are recommended).
- Foreign keys and constraints for integrity.
- Explicit timestamps, status values and provenance.
- Separate identity/authentication from church-person records.
- Separate a person's visitor history from formal membership.
- Least-privilege access through RLS.
- Avoid collecting unnecessary personal or sensitive data.
- Preserve an auditable history of important changes.
- Version every schema change using SQL migrations.

## 2. Proposed logical entities

Names below are conceptual and may change during schema review.

### Identity and administration
- `admin_profiles`: application profile linked to Supabase Auth user ID.
- `roles`: named role definitions.
- `permissions`: individual capabilities.
- `role_permissions`: role-to-permission mapping.
- `user_roles`: role assignments.
- `user_permission_overrides`: explicit grants/revocations where needed.
- `membership_approvers` or equivalent permission assignment: explicit designation of users authorised to approve membership.
- `audit_logs`: actor, action, target, timestamp and safe metadata.

Supabase Auth's internal user table remains managed by Supabase; do not duplicate passwords or authentication secrets.

### People and membership
- `people`: core person/contact record.
- `visitor_records`: visit/visitor context and registration source.
- `membership_records`: formal membership status and relevant dates.
- `membership_decisions`: approval decision, approver, timestamp and permitted reason metadata.
- `departments`: department definitions.
- `department_memberships`: person-to-department assignments and role within department.

A person may have a visitor record before a membership record. Do not equate form submission with membership.

### Follow-up and pastoral care
- `follow_up_tasks`: assignment, due date, status and related person.
- `follow_up_notes`: restricted notes and action history.
- `prayer_requests`: request content, privacy/publication status and lifecycle.
- `prayer_assignments`: authorised assignment of a request.

Prayer text and notes require more restrictive policies than ordinary public content.

### Public content
- `announcements`
- `events`
- `sermons`
- `media_assets`
- `livestreams`
- `leadership_profiles`
- `service_schedules`

Published public content may be readable anonymously; drafts and unpublished content must not be.

### Registration and analytics
- `registration_submissions` or a suitable intake record.
- `registration_sources`
- `page_view_events` and `interaction_events`, if approved.
- Aggregated reporting views/materialised aggregates as justified.

Do not store raw IP addresses or detailed behavioural profiles unless a documented necessity, lawful basis, retention period and security plan are approved.

### Future modules (not initial implementation)
- `attendance_sessions`
- `attendance_records`
- `financial_accounts`
- `financial_transactions`
- `giving_records`
- `volunteers`
- `volunteer_assignments`

Financial tables must have their own restricted access model and should not be exposed to ordinary department administrators.

## 3. Key relationships

- One person may have multiple visitor interactions.
- A person may have zero or one current formal membership record, subject to the final membership-history design.
- A person may belong to multiple departments.
- An admin profile maps to an authenticated Supabase user.
- An admin user may hold multiple roles.
- A role grants a defined set of permissions.
- Membership approval is granted explicitly and independently of department membership.
- A follow-up task belongs to a person and may be assigned to an admin.
- A prayer request may have one or more authorised assignments.
- Content records track their author/editor and publication state.

## 4. Membership decision data

At minimum, each membership decision must retain:
- Membership/person reference.
- Decision outcome.
- Approver's authenticated user ID.
- Decision timestamp generated by the trusted backend/database.
- Optional reason/comment only if the church approves its collection.
- Relevant audit event.

The system must reject a decision if the acting user lacks the explicit membership-approval permission. A browser-supplied approver ID must never be trusted as proof of authority.

## 5. Data quality and duplicate handling

- Normalise phone numbers to a consistent format where possible.
- Use case-insensitive email matching where appropriate.
- Do not assume two people are identical because they share a phone number or email.
- Present likely duplicates for human review.
- Keep a record of merge decisions if record merging is later implemented.
- Validate dates, status transitions and required fields.
- Use database constraints for invariants that must always hold.

## 6. Security classification

| Classification | Examples | Access |
|---|---|---|
| Public | Published events, approved service details | Anonymous read |
| Internal | Draft announcements, admin work queues | Authorised staff |
| Personal | Phone, email, birthday, membership details | Explicitly authorised roles |
| Restricted pastoral | Private prayer requests, follow-up notes | Specifically authorised personnel |
| Security-sensitive | Audit logs, role grants, credentials/secrets | Very limited administrators/system |

## 7. Migration strategy

- Create SQL migrations in chronological, version-controlled files.
- Never edit an already-applied production migration; add a corrective migration.
- Test migrations against a non-production project.
- Keep seed data fictional and clearly marked.
- Do not commit real member data or production exports.
- Document rollback considerations for destructive changes.

## 8. Open schema decisions

The exact status vocabulary, membership-history rules, retention periods, data export rules, department structure and prayer-request assignment rules require church approval. Final SQL should not be written until these are resolved and the access-control design is reviewed.
